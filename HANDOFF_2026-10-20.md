## Stage 1: simple SD actuation bench test

Environment: actuation_sd, serial 57600, same valve_log_console.py protocol as dwell_test.

This program MOVES THE VALVE after START. Unlike the calculation-only reference, it is motor firmware. It logs motor telemetry only; it does not require or read PT channels. SD CS is configured as 9. Confirm actual wiring, SPI sharing, motor zero/reference, motor ID, power and the team's test procedure before uploading on an inactive setup.

After PC time synchronization and successful SD initialization, START enters a five-second closed interval, then performs five cycles: open, hold open five seconds after fresh position feedback confirms arrival, close, and wait five seconds before the next cycle. Travel timeout is one second. It requests position targets/heartbeats at 20 ms intervals (50 Hz) and samples logging at a requested 10 ms (100 Hz). Fresh finite position feedback within 0.15 motor rotations is required to recognize arrival. These are test settings, not a demonstrated control timing guarantee.

The original test's terminal closed-target behavior remains: after completion or travel timeout, it keeps requesting the existing closed target. A timeout is reported as ACTUATION_TIMEOUT. There is no new automatic valve-close action associated with logging STOP or an SD failure. STOP stops recording only; the actuation sequence can continue to move the valve. This is not an emergency-stop command.

The program requests log closure automatically at completion/timeout, including a final state row when space permits. Use STATUS to inspect diagnostics. The console may still say the session is running after automatic closure; STOP confirms the closed log and its final report. Closing/disconnecting the console is not a substitute for the operator's end-of-test procedure.

Normal console use after approved firmware upload:

    python valve_log_console.py --port COMx

Confirm the actual port; CONNECT synchronizes time, START moves the valve, STATUS retrieves logging diagnostics, STOP stops logging only. A successful LOG_CLOSED message does not prove there were no dropped samples. Review missed_log_slots, queue_full_records, oversized_records, max_write_us, close_us, max_loop_gap_us, max_heartbeat_gap_us and max_command_gap_us. Also inspect motor freshness and the resulting CSV. Feedforward flow testing follows only after the team evaluates this bench test.

Preallocation, write, truncate/close and SD card behavior can still block the single control loop. The 5 ms diagnostic threshold is retained from the original task; the 20 ms command schedule remains unchanged. These requirements still need clarification and hardware measurement. No bench, pressure, cryogenic or CAN-bus validation has been performed by the assistant.

## Stage 2: understand the feedforward model

Input: upstream absolute pressure, desired downstream absolute pressure, and outlet absolute backpressure. Assumption: steady single-phase incompressible liquid passes through a valve followed by a fixed restriction. The outlet model is an explicit placeholder, not a confirmed CTS characterization.

    required valve CdA = outlet CdA * sqrt((target - backpressure)/(upstream - target))

Then invert the valve-angle/CdA table by linear interpolation. The angle is valve degrees, not motor revolutions. The model does not send that angle anywhere. The sample table and outlet CdA are synthetic. Density cancels in this ratio but is used to report predicted mass flow. It is not a measured flow rate.

Explain these before proceeding:

1. Why does the model need an outlet restriction as well as a valve table?
2. With 500000/300000/100000 Pa absolute and outlet CdA 5 mm^2, why is required valve CdA 5 mm^2?
3. Why does the synthetic table then return 30 degrees? What angle should it return for 7.5 mm^2?
4. Why must invalid results NOT be converted into motor commands? What does AboveTable mean?
5. What is the difference between gauge PSI and absolute Pa? Which reference do the actual PTs use?
6. Which part of the system is still closed loop during a feedforward-only test? Answer: the motor's position loop; the outer pressure correction is disabled.

Answers to the numeric examples: 30 degrees for 5 mm^2; 35 degrees for 7.5 mm^2. These are examples, not real-valve operating recommendations.

## Stage 3: profiles without motor commands

Each profile point contains elapsed milliseconds, a dimensionless level from 0 to 1, and whether to hold or linearly interpolate toward the next point. Time starts at zero and increases strictly. Values must stay finite and within 0..1. At the final point the sampler returns Finished and the final level; it does not restart, stop the motor, close the valve, or impose a zero value.

Change FEEDFORWARD_PROFILE_ID in include/feedforward_profiles.h and rebuild:

- 0: steady example, level 0.5 for 10 seconds.
- 1: ramp example, 0 to 1 over 10 seconds, then back to 0 over 10 seconds.
- 2: stepped placeholder, 0.25, 0.75, then 0.4 with illustrative timings.

The existing calculation reference accepts PROFILE,<elapsed_ms> at 115200 baud. It prints one sample without waiting or controlling hardware. For ramp selection 1, PROFILE,5000 should report 0.5, PROFILE,10000 should report 1.0, and PROFILE,20000 should report Finished at 0.0. This previews a timeline, not a calibrated thrust/pressure trajectory.

There is intentionally no default conversion from profile level to pressure. A level of 0.5 must NOT be assumed to mean half the valve angle or half the absolute downstream pressure. Noah must specify the mapping, required pressures, ranges, timing, and end-of-profile behavior. Zero requested thrust is not automatically a motor-close instruction in this library.
